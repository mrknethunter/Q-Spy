# E-05 — Hardware diagnostics: fidelity, concentration and drift

## Scope and current state

E-05 reads Bloch-vector runs already stored by I-04. It does not execute circuits
or submit QPU jobs. A campaign is accepted only when its run IDs follow the H-02
manifest convention, its tiers and experiment groups are complete, its IDs match
the D-05 subsets, and its `embed_config` agrees with the frozen L-05 values.
The run names alone are not enough: HW metadata must include job IDs, backend
name and calibration information.

The current checkout's D-05 JSON has status `draft_pending_l05` and no
`l05_freeze` binding. The D-05 lifecycle documents still describe a
draft/review proposal without final acceptance, and the decision record labels
L-05 as a draft for lead approval. E-05 reports these as pending approvals.
The frozen embedding configuration is `n=8`, `L=2`, `s=0.1778`, precision
`0.03`, with concentration qubits `4, 8, 12`, and does not define `gamma`. The
store contains H-01 pilot runs, but no complete H-02 campaign. E-05 deliberately
does not treat the pilot as H-02.

G-03 (`diagnostics/compare.py`) is integrated from `origin/main` by merge commit
`6b237e3` on `E-05-task`. Its public API is imported directly; E-05 does not
copy or reimplement G-03. The E-05 integration tests for float32 and float64
now execute against that module. The source task cards remain workspace exports
outside this checkout; they are not versioned under `tasks/` in this branch.
The proposal PDF used for context is `documentazione/Q-Spy_Project.pdf` in the
workspace.

## Architecture and reused components

- `experiments/e05/analysis.py` discovers and validates campaign runs, invokes
  the shared calculations and records missing prerequisites.
- `store.io.read_bloch` is the only store reader (I-04).
- `data.hardware_subsets.load_hardware_subsets(freeze_repo=...)` uses the
  strict lifecycle and verifies the recorded binding against the live
  `hw-freeze` tag, so a draft or moved tag cannot be used silently.
- `kernels.projected.projected_kernel` builds the projected kernel (M-01). The
  frozen bandwidth `s` is not applied a second time; it is already part of the
  stored Bloch vectors.
- `diagnostics.concentration` supplies `off_diagonal_values`,
  `off_diagonal_variance`, `eigen_spectrum` and `effective_rank` (G-01).
- `diagnostics.compare` supplies `bloch_frobenius_error`, `kernel_alignment`,
  `compare_runs` and `drift_report` (G-03). Missing G-03 is surfaced in the
  report rather than implemented again in E-05.

Run matching follows the H-02 writer's IDs:
`hw-<UTC campaign>-<experiment>-<tier>`, with experiment names `main`,
`control`, `concentration-n4/n8/n12`, `drift-start` and `drift-end`. L0 and HW
must cover exactly the same D-05 IDs. The run's tier, stored run ID, sample
count, embedding configuration and HW provenance metadata are also checked.
Row ordering may differ; the G-03 comparison receives the original IDs and
performs the ID-based alignment.

At the I-04 boundary, E-05 requires `ids` to be a list of non-empty strings,
with unique values and a length equal to the Bloch array's leading dimension.
It does not coerce IDs to strings. A malformed run is excluded and reported
under `store_errors` with its run ID and validation reason.

The H-02 writer does not emit `source_kind`, so E-05 does not require that
field. When present, its only accepted values are `hardware` and
`synthetic_fixture`. When it is absent, E-05 infers `hardware` only if all
required H-02 hardware metadata for that run passes validation; otherwise the
run provenance is `unverified` and the campaign is rejected. Unknown values
are rejected. A campaign containing both hardware and fixture HW runs is
marked `mixed_provenance` and cannot be selected. Source details are included
in the campaign analysis for traceability.

Every run matching a campaign prefix is retained during discovery. More than
one run for the same `(experiment, tier)` makes that campaign invalid; E-05
reports the campaign, pair and all run ID occurrences, and does not choose a
run based on store order.

## Metrics and gamma

For each matched group, E-05 reports the G-03 per-qubit Bloch RMSE, global RMSE
and Frobenius norm. It validates the stored Bloch arrays against L-02 before
constructing kernels, accepts float32 or float64 without converting the stored
array, and checks that each run's Bloch qubit dimension matches its declared
embedding configuration. With an approved gamma value in the frozen config,
it builds L0 and HW projected kernels through M-01, reports G-03 centered
normalized Frobenius alignment, and computes G-01 off-diagonal population
variance (`ddof=0`), eigen-spectrum and effective rank. Drift uses the H-02 HW
`drift-start` and `drift-end` runs with G-03 `drift_report`. No acceptance
thresholds are introduced.

Gamma is not present in the frozen config on this branch. The L-05 decision
record describes a training-only selection procedure (`c / median(d²_train)`
with `c` selected from the documented grid), but E-05 has no approved gamma
selection artifact or shared API that supplies its selected value and
provenance. E-05 therefore does not accept an arbitrary CLI gamma or choose
one from hardware evaluation points. Kernel alignment and concentration
remain unavailable until an approved value is present in the frozen config.

## Inputs, outputs and commands

Run commands from the repository root:

```bash
.venv/bin/python -m experiments.e05.cli analyze
.venv/bin/python -m experiments.e05.cli analyze --campaign-id hw-20261124T010203Z --run-id review-01
.venv/bin/python -m experiments.e05.cli figures results/e05/runs/<run-id>
.venv/bin/python -m experiments.e05.cli summary results/e05/runs/<run-id>
```

The first command generates a timestamp-isolated directory under
`results/e05/runs/` with `analysis.json`, `summary.md`, and only those SVGs whose
metrics were available. The `figures` command regenerates SVGs from the saved
analysis JSON; `summary` regenerates the Markdown page. All plots are written by
Python using the standard library, so Matplotlib is not required. Missing plots
and their reasons are stored in `analysis.json` and listed in the summary.

The report distinguishes `hardware`, `synthetic_fixture` and unavailable data.
An injected subset object or a fixture-marked campaign is explicitly not
hardware validation. For H-02 hardware runs, E-05 checks job IDs, backend,
calibration snapshot, physical layout, two-qubit depth, precision, usage,
estimated usage and mitigation settings emitted by `quantum.embed` and
`scripts/qpu_campaign.py`. It does not require a `job_status` field. Output
directories are unique by default and are never silently reused by `analyze`.
The `analyze` command still exits with code 0 when the JSON report says
`blocked_by_prerequisites`; automation should inspect `analysis.json`'s
`status` field. Changing that exit-code behavior is an interface decision and
is not part of the current implementation scope.

## Tests and limitations

Run the E-05 tests with:

```bash
.venv/bin/python -m pytest tests/e05 -q
```

Tests write temporary I-04 runs, exercise D-05 ID matching, campaign
provenance and duplicate detection, and verify malformed IDs are surfaced in
the report without coercion. G-01 tests compare off-diagonal values and
population variance with hand-calculated values, and check a known PSD
eigen-spectrum, entropy effective rank, zero/rank-one kernels, the small
negative-eigenvalue tolerance and rejection of a non-PSD kernel. These tests
call the real `diagnostics.concentration` API; E-05 does not copy its
algorithms. Isolated metric orchestration uses an explicitly named G-03 test
double. The public G-03 integration tests ran against both float32 and float64
inputs in this checkout. Figure and summary scripts are exercised on synthetic
fixtures; those artifacts validate generation and determinism only and are not
hardware results. No test claims to validate H-02 hardware. On 25 November
2026, the permitted focused runs passed: `tests/e05` (35), `tests/test_compare.py`
(33), `tests/test_store.py` (4), and the M-01 projected-kernel contract test (1).

Current data-dependent limitations: D-05 and L-05 approvals are pending, no
H-02 campaign runs are present, and no gamma selection is approved or frozen.
G-03 is available in this branch, so its absence is no longer a blocker.
Without the H-02 campaign and approvals E-05 cannot produce hardware diagnostic
figures or claim hardware validation. The D-05 subset loader continues to
enforce the recorded lifecycle and freeze binding; a pending status is not
treated as approval. No H-01 data are substituted, no store data are changed,
and no QPU jobs are submitted by E-05.

The general code review, including observations outside the corrective scope,
is recorded separately in `docs/E05_GENERAL_REVIEW.md`. Those observations are
diagnostic and have not been implemented here.
